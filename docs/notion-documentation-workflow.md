# Notion 文案整理流程

## 1. 目的

把讨论、实现、测试和运行结果整理成可维护的 Notion 文档，同时避免以下常见问题：

- 把规划当成已经实现；
- 把代码存在当成玩家行为已经可用；
- 旧结论覆盖新证据；
- 在当前节点文档中提前设计后续节点；
- Notion、README 和代码边界互相矛盾。

## 2. 必要输入

每次整理前明确：

1. 目标页面与目标读者；
2. 本次只整理哪个节点或版本；
3. 权威规格或用户已确认决策；
4. 代码、测试、构建和运行证据；
5. 明确不展开的内容；
6. 需要保留的 Notion 子页面、关联页面、图片和数据库。

## 3. 标准流程

### 步骤一：读取现有页面

- Fetch 目标页面全文。
- Fetch 页面直接引用的规格、体验和决策页面。
- 搜索同名或相近文档，避免重复创建。
- 记录必须保留的子页面和关系块。

### 步骤二：建立事实基线

按以下优先级判断：

1. 用户在当前对话中明确确认的规则；
2. 可运行行为和端到端证据；
3. 自动测试、构建和静态检查；
4. 当前代码与配置；
5. 旧文档中的描述。

旧文档与高等级证据冲突时，更新旧文档，并在必要时记录偏差。

### 步骤三：给每条内容分类

| 分类 | 写法 |
|---|---|
| 已确认目标 | 使用确定语气，并链接规格来源 |
| 已实现且直接验证 | 写明行为、实现位置和验证层级 |
| 已实现但未接入 | 明确写“代码存在，尚未进入目标流程” |
| 合理推断 | 标记为推断，不写成完成事实 |
| 当前限制 | 描述缺口，不自动扩写解决方案 |
| 后续节点 | 用户未要求设计时只写“本页不定义” |

### 步骤四：按固定结构重写

默认使用：

1. 一句话摘要；
2. 范围与非范围；
3. 当前用户流程；
4. 关键规则；
5. 系统职责与边界；
6. 实现文件索引；
7. 运行方式；
8. 验证证据；
9. 当前限制；
10. 关联页面与变更记录。

删除已经被真实实现取代的阶段性计划，除非其仍作为历史决策有价值；有价值的旧内容移动到折叠区或暂停页面。

### 步骤五：更新 Notion

- 先创建需要独立复用的流程页或参考页。
- 更新正文时保留仍有价值的 page、database 和 mention 关系。
- 页面标题反映当前内容，不继续使用含混的“代码实现”。
- 不在正文中暴露密钥、私人配置或临时签名链接。

### 步骤六：回读验证

更新后重新 Fetch 页面，逐项检查：

- 标题和章节顺序正确；
- 没有误删子页面或关联页面；
- 完成状态与代码和测试一致；
- 运行命令可以直接复制；
- 当前节点没有混入未授权的后续设计；
- README、仓库文档和 Notion 没有互相冲突。

## 4. 可复用正文模板

```markdown
<callout icon="✅" color="green_bg">
    一句话说明当前节点已经解决什么，以及本文不覆盖什么。
</callout>

## 范围

## 当前状态

## 玩家 / 用户流程

## 关键规则

## 系统职责与边界

## 实现位置

## 运行方式

## 验证证据

## 当前限制

## 关联页面

## 文档变更记录
```

## 5. 完成检查清单

- [ ] 页面只有一个明确版本或节点范围。
- [ ] 每项“已完成”都有代码或运行证据。
- [ ] 已实现未接入的内容被单独标明。
- [ ] 没有把后续设想伪装成当前行为。
- [ ] 命令、文件路径和接口字段与仓库一致。
- [ ] 相关页面和子页面关系仍然保留。
- [ ] 更新后已经回读验证。
